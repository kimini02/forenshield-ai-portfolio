# 포렌식 사건 분석 UX 단계별 구현 계획

상위 기준 문서:

```text
docs/FORENSIC_CASE_ANALYSIS_UX_POLICY.md
```

이 문서는 상위 UX 정책을 한 번에 구현하지 않고, 충돌과 회귀를 줄이기 위해 단계별로 나눠 진행하기 위한 작업 계획입니다.

현재 이미 반영된 작업:

```text
/cases/{caseId}와 /evidences/{evidenceId} 라우트 분리
마이페이지 caseId가 evidenceId로 섞이지 않도록 백엔드 보정
증거 상세 응답 호환 필드 일부 정리
```

## 1단계: 메인 분석 화면 문구와 세션 의미 정리

목표:

```text
사용자가 업로드 완료, 분석 요청 완료, 분석 완료를 혼동하지 않게 한다.
초기화 버튼의 의미를 "서버 삭제"가 아니라 "새 사건 시작"으로 명확히 한다.
```

프론트 작업:

```text
[x] "초기화" 버튼 이름을 "새 사건 시작"으로 변경
[x] 새 사건 시작은 프론트 로컬 업로드 세션만 초기화하도록 유지
[x] 서버의 Evidence, AnalysisRequest, CoC 로그는 삭제하지 않음
[x] 업로드 완료 문구와 분석 요청 완료 문구를 분리
[x] 분석 상태 표기에서 PENDING은 "분석 대기", PROCESSING은 "분석 중", COMPLETED는 "분석 완료"로 구분
[x] 분석 요청 성공 후 "새 사건 시작" 액션을 명확히 노출
```

백엔드 작업:

```text
[x] 없음
```

백엔드에서 하지 않을 것:

```text
초기화 API 추가
업로드 세션 삭제 API 추가
분석 완료 기록 삭제
```

검증:

```text
[x] 업로드 완료 후 화면에서 "분석 완료"로 오해되는 문구가 없는지 확인
[x] 분석 요청 성공 후 기록은 남고, 새 사건 시작 시 화면만 비워지는지 확인
[x] pnpm build 통과
```

## 2단계: 사건명 필수 UX 적용

목표:

```text
증거가 처음 저장될 때부터 사건 기준을 갖게 한다.
사건명 없는 업로드로 인해 마이페이지/사건 상세 기준이 흔들리지 않게 한다.
```

프론트 작업:

```text
[x] 사건명 입력값이 비어 있으면 파일 업로드 버튼 비활성화
[x] 이미 파일 선택 후 사건명을 지우면 업로드 시작 불가
[x] 에러 문구: "사건명을 입력해 주세요."
[x] 사건명 입력 필드를 "사건명" 또는 "사건명/사건 식별자"로 명확히 표시
```

백엔드 작업:

```text
[x] FileService.upload(...) 또는 EvidenceController 업로드 API에서 caseName blank 검증
[x] caseName blank면 400 응답
[x] 에러 메시지: "사건명을 입력해 주세요."
```

백엔드에서 하지 않을 것:

```text
Cases 테이블 추가
AnalysisService.startAnalysis(...)에서 사건명 정책 변경
기존 Evidence의 caseName 일괄 마이그레이션
```

검증:

```text
[x] 사건명 없이 업로드 시 프론트에서 버튼 비활성화
[x] API 직접 호출로 사건명 없이 업로드하면 400
[x] 사건명 입력 후 여러 파일 업로드 가능
[x] sh gradlew test 통과
[x] pnpm build 통과
```

## 3단계: 새 사건 / 기존 사건 탭 분리

목표:

```text
사용자가 새 사건을 시작하는지, 기존 사건에 증거를 추가하는지 명확히 선택하게 한다.
```

프론트 작업:

```text
[ ] 메인 분석 화면에 "새 사건" / "기존 사건" 탭 추가
[ ] 새 사건 탭: 사건명 입력 + 파일 업로드
[ ] 기존 사건 탭: 기존 사건 선택 UI 추가
[ ] 기존 사건 선택 시 해당 caseId/caseName으로 업로드
[ ] 기존 사건에 증거 추가 후 분석 시작 가능
```

백엔드 작업:

```text
[ ] 기존 사건 목록 API가 충분한지 확인
[ ] 부족하면 현재 사용자 사건 목록을 가볍게 조회하는 API 추가 검토
```

백엔드에서 하지 않을 것:

```text
사건 전용 테이블 생성
사건 자체 분석 요청 생성
```

검증:

```text
[ ] 새 사건 탭에서 새 caseName으로 업로드 가능
[ ] 기존 사건 탭에서 선택한 사건으로 업로드 가능
[ ] 마이페이지 사건 목록에서 같은 사건으로 묶이는지 확인
[ ] pnpm build 통과
```

## 4단계: 사건 상세 페이지 안정화

목표:

```text
/cases/{caseId}는 사건 상세만 담당한다.
사건 상세에서 증거 목록을 보고 증거 상세로 이동한다.
```

프론트 작업:

```text
[ ] 사건 상세에서 사건명, 상태, 생성일 표시
[ ] 사건 상세에서 증거 목록 표시
[ ] 증거 클릭 시 /evidences/{evidenceId} 이동
[ ] 증거별 분석 상태 표시
[ ] 증거 추가 버튼 위치 확정
```

백엔드 작업:

```text
[ ] /api/v1/cases?caseKey=... 응답 안정화 확인
[ ] evidences 배열이 null이 아니라 []로 내려오는지 확인
[ ] evidences[].evidenceId 포함 유지
```

백엔드에서 하지 않을 것:

```text
사건 상세에서 분석 결과 전체를 한 번에 합산하는 복잡한 API 추가
```

검증:

```text
[ ] 마이페이지 사건 클릭 시 /cases/{caseId} 정상 표시
[ ] 숫자처럼 생긴 caseId도 증거 상세로 오인하지 않음
[ ] 사건 안의 증거 클릭 시 /evidences/{evidenceId} 정상 표시
```

## 5단계: 증거 상세 페이지 안정화

목표:

```text
/evidences/{evidenceId}는 증거 하나의 해시, 메타데이터, 분석 결과, CoC, 보고서 영역을 담당한다.
```

프론트 작업:

```text
[x] 증거 정보 영역 정리
[x] 무결성/해시 영역 정리
[x] 분석 상태 영역 정리
[x] moduleResults가 []일 때 빈 상태 표시
[x] cocLogs가 []일 때 빈 상태 표시
[x] PDF 보고서 영역 placeholder 추가
```

백엔드 작업:

```text
[x] /api/v1/evidences/{evidenceId}/detail 응답에서 moduleResults: [] 보장
[x] cocLogs: [] 보장
[x] integrityInfo.chainValid, isChainValid 호환 유지
[x] evidenceInfo.mediaType, fileType 호환 유지
```

백엔드에서 하지 않을 것:

```text
PDF 생성 API를 이 단계에서 구현하지 않음
복사본 삭제 버튼 API를 만들지 않음
```

검증:

```text
[x] 분석 미완료 증거 상세도 화면이 깨지지 않음
[x] 분석 완료 증거 상세에서 분석 결과가 표시됨
[x] pnpm build 통과
```

## 6단계: 원본 증거 삭제 요청 UX

목표:

```text
원본 증거 삭제와 프론트 화면 초기화를 분리한다.
포렌식 감사 이력을 보존한다.
```

프론트 작업:

```text
[ ] 증거 상세에 "원본 증거 삭제 요청" 버튼 추가
[ ] 사건 상세 증거 목록에도 삭제 요청 액션 위치 검토
[ ] 삭제 확인 모달 추가
[ ] 분석 중/대기 상태에서는 삭제 불가 안내
[ ] 삭제 후 목록에서 숨김 처리
```

백엔드 작업:

```text
[ ] 원본 증거 soft delete 정책 확인
[ ] Evidence.deletedAt, status=DELETED 기준 유지
[ ] 분석 중/대기 상태 삭제 불가 정책 적용
[ ] 삭제 관련 감사/CoC 이벤트명은 ERD 기준 검토 후 확정
```

백엔드에서 하지 않을 것:

```text
원본 파일 물리 삭제 즉시 수행
AnalysisRequest, AnalysisResult 물리 삭제
CoC 로그 삭제
```

검증:

```text
[ ] 분석 중/대기 증거 삭제 요청 시 차단
[ ] 삭제 가능 증거는 soft delete
[ ] 삭제 후 일반 목록에서 숨김
[ ] 관리자/감사 기록은 보존
```

## 7단계: PDF 보고서 UX/API

목표:

```text
분석 완료 후 포렌식 분석 결과를 PDF 보고서로 생성하고 다운로드한다.
다운로드 횟수를 제한하지 않고 다운로드 이력을 남긴다.
```

프론트 작업:

```text
[ ] 분석 완료 전 PDF 버튼 비활성화
[ ] 분석 완료 후 보고서가 없으면 "PDF 보고서 생성" 버튼 표시
[ ] 보고서 생성 완료 후 "PDF 다운로드" 버튼 표시
[ ] reportHash, 생성일, 생성자 표시 영역 추가
```

백엔드 작업:

```text
[ ] 보고서 생성 API 추가
[ ] PDF 다운로드 API 추가
[ ] Reports 저장
[ ] reportHash 저장
[ ] REPORT_CREATED CoC 로그 저장
[ ] REPORT_DOWNLOADED CoC 로그 저장
```

백엔드에서 하지 않을 것:

```text
PDF 다운로드 1회 제한
다운로드 시 보고서 삭제
보고서 다운로드 이력 생략
```

검증:

```text
[ ] 분석 미완료 상태에서는 보고서 생성 불가
[ ] 분석 완료 후 보고서 생성 가능
[ ] PDF 다운로드 여러 번 가능
[ ] 다운로드마다 REPORT_DOWNLOADED 로그 저장
```

## 8단계: 분석용 복사본 상태 표시

목표:

```text
분석용 복사본은 시스템이 자동 삭제한다.
프론트는 버튼을 만들지 않고 상태만 읽기 전용으로 보여준다.
```

프론트 작업:

```text
[ ] 증거 상세 기술 정보에 복사본 상태 표시 여부 검토
[ ] 표시한다면 copyStatus, copyDeletedAt, copyHashValue 읽기 전용 표시
[ ] 복사본 삭제 버튼은 만들지 않음
```

백엔드 작업:

```text
[ ] 분석 완료 후 복사본 자동 삭제
[ ] copyStatus=DELETED, copyDeletedAt 저장
[ ] ANALYSIS_COPY_DELETED CoC 로그 저장
```

백엔드에서 하지 않을 것:

```text
복사본 수동 삭제 API
복사본 삭제 버튼용 API
사용자에게 복사본 삭제 권한 부여
```

검증:

```text
[ ] 분석 완료 후 복사본이 자동 삭제됨
[ ] 증거 상세에서 복사본 상태가 읽기 전용으로 표시됨
[ ] CoC에 ANALYSIS_COPY_DELETED 표시됨
```
